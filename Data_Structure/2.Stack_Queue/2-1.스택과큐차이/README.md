# 스택과 큐의 차이

> - 스택은 LIFO(후입선출), 큐는 FIFO(선입선출)로 데이터를 꺼내는 순서가 정반대
> - 스택은 되돌리기·호출 스택처럼 마지막 상태로 돌아가는 곳, 큐는 작업 대기열·버퍼처럼 들어온 순서를 보존하는 곳에 쓰임
> - 직접 구현한다면 큐는 LinkedList, 스택은 배열이 적합하지만, Java에서는 둘 다 ArrayDeque를 권장

## 스택과 큐의 차이

둘 다 한쪽 끝에서 데이터를 넣지만, 꺼내는 위치가 달라 출력 순서가 정반대다.

|    구분    |       스택 (Stack)        |         큐 (Queue)         |
|:--------:|:-----------------------:|:-------------------------:|
|  입출력 원칙  |       LIFO (후입선출)       |        FIFO (선입선출)        |
| 삽입/삭제 위치 |    같은 끝(top)에서 넣고 뺌     | 뒤(rear)에서 넣고 앞(front)에서 뺌 |
|  주요 연산   | `push` / `pop` / `peek` | `offer` / `poll` / `peek` |

## 활용 예시

| 자료구조 |                    실무 예                    |                 이유                  |
|:----:|:------------------------------------------:|:-----------------------------------:|
|  스택  |  함수 호출 스택, Undo/Redo, 브라우저 뒤로가기, 괄호·태그 매칭  | 가장 최근 상태로 되돌아가야 하므로 마지막 것이 먼저 나와야 함 |
|  큐   | 메시지 큐(Kafka), 스레드풀 작업 대기열, 요청 버퍼링, 프린터 스풀러 |    먼저 들어온 작업을 먼저 처리해 공정성·순서를 보존     |

### 스택 - 호출 스택의 내부

스택의 대표 사례는 호출 스택(call stack)이다.

- 메서드를 호출하면 스택 프레임이 push되고, 이 프레임에 지역 변수·매개변수·복귀 주소(return address)가 담김
- `return`을 만나면 가장 위 프레임을 pop하고 복귀 주소로 점프 → 호출의 역순으로 정리되는 전형적인 LIFO
- 재귀가 너무 깊어 프레임이 스택 크기 한계를 넘으면 `StackOverflowError` 발생

### 큐 - 스레드풀 대기열의 내부

큐의 대표 사례는 스레드풀의 작업 대기열이다.

- `ThreadPoolExecutor`는 내부에 `BlockingQueue`를 두고, 제출된 작업을 들어온 순서대로 워커 스레드에 전달
- 생산 속도가 소비 속도보다 빠를 때 큐가 버퍼 역할을 해 순간적인 부하를 받아냄
- 큐가 가득 차면 `RejectedExecutionHandler` 정책(예: `CallerRunsPolicy`)으로 backpressure를 거는 지점

## LinkedList로 만들 때 스택과 큐 중 무엇이 적합한가

### 큐를 LinkedList로 구현한 이유

큐는 넣는 입구(rear)와 빼는 출구(front)가 나뉜 FIFO 구조라, 배열로 만들면 이 구조 때문에 성능이 떨어진다.

- dequeue 때 맨 앞(0번 인덱스)을 비운 뒤, 남은 요소를 전부 한 칸씩 앞으로 당겨야 함 → O(n)
- front에서 빼는 동작이 잦은 큐에서는 이 시프트가 계속 쌓여, 큐가 커질수록 느려짐

```text
배열 큐에서 맨 앞(A) 제거:
[A][B][C][D]
[B][C][D][ ]   ← B·C·D를 한 칸씩 앞으로 이동 (O(n))
```

LinkedList는 이 이동 자체가 없어서 front 삭제를 O(1)로 처리할 수 있다.

- head·tail 포인터만 두면 front 삭제는 head를 다음 노드로 옮기는 것으로 끝나 O(1)
- 양 끝 삽입·삭제가 모두 요소 이동 없이 O(1)이라, front 삭제가 잦은 큐에 잘 맞음

### 스택을 LinkedList로 구현하지 않는 이유

스택은 한쪽 끝(top)에서만 넣고 빼는 LIFO라, 배열 끝의 추가·삭제든 LinkedList든 똑같이 O(1)지만, 메모리·캐시 효율은 배열이 훨씬 유리하다.

- 메모리 효율
    - 배열: 한 요소에 데이터 참조값 한 칸만 필요
    - LinkedList: 노드마다 데이터 참조 외에 앞뒤 포인터 2개, 객체 헤더, 정렬 패딩이 붙어 항목당 3~4배 많은 메모리를 씀
- 캐시 지역성
    - 배열: 요소가 메모리에 연속 배치돼, CPU가 한 줄을 통째로 캐시에 올리는 특성과 맞아 적중률이 높음
    - LinkedList: 노드가 힙 곳곳에 흩어져, 다음 노드를 따라갈 때마다 캐시 미스가 잦아 실제 속도가 느림
- 리사이징 비용
    - 배열은 꽉 차면 더 큰 배열로 복사하지만, 용량을 일정 비율로 늘리는 방식으로 횟수를 줄임

실제로 자바에서 스택으로 쓰는 구현체도 내부는 모두 배열이다.(레거시 `Stack`은 `Vector`=배열 기반, 권장되는 `ArrayDeque`는 원형 배열)

다만 메모리 회수 한 가지는 LinkedList가 유리하다.

- pop으로 빠진 노드는 곧바로 GC 대상이 되어 그만큼의 메모리가 즉시 회수됨
- 배열은 스택이 줄어도 한번 늘린 용량을 유지해, 비어 있는 칸만큼의 공간을 계속 점유

### 정리

자료구조 원리상의 선택이 이렇다는 것이고, 실무에서 직접 구현할 일은 거의 없으며, Java에서는 스택·큐 모두 `ArrayDeque`를 쓰는 것이 공식 권장 방식이다.

- Java의 `Stack`은 1.0 시절의 레거시라 권장하지 않으며, 스택·큐 모두 배열 기반 양방향 큐인 `ArrayDeque`를 쓰는 것이 공식 권장
- `ArrayDeque`는 위에서 본 배열 큐의 시프트 문제를 원형 배열로 회피
- 요소를 연속된 메모리에 담아 LinkedList처럼 노드가 힙 곳곳에 흩어지지 않아 순회·접근이 빠름(캐시 지역성)

> `ArrayDeque` 클래스 javadoc  
> likely to be faster than `Stack` when used as a stack, and faster than `LinkedList` when used as a queue.

## 꼬리 질문 - 스택과 큐 특징을 모두 쓰고 싶다면?

양쪽 끝에서 삽입·삭제가 모두 가능한 덱(Deque, Double-Ended Queue)을 쓴다.

한쪽 끝만 쓰면 스택, 양 끝을 쓰면 큐가 되므로 덱 하나로 둘을 모두 표현할 수 있다.

|   사용법   |             호출             |  동작  |
|:-------:|:--------------------------:|:----:|
| 스택처럼 쓰기 | `addFirst` + `removeFirst` | LIFO |
| 큐처럼 쓰기  | `addLast` + `removeFirst`  | FIFO |

- Java에서는 `Deque` 인터페이스가 이 역할을 하며, 구현체로 `ArrayDeque`(권장)와 `LinkedList`가 있음
- 스택이 필요할 때 레거시 `Stack` 클래스 대신, 큐가 필요할 때 `LinkedList` 대신 `ArrayDeque`를 쓰는 것이 현재 권장 방식
